# Phase 0 courte — S2 : mode objectif, comparaison de scénarios, résultat observé à J+30 (2026-09-24)

Lecture seule. Périmètre : les trois compléments du Simulateur reportés à S2 (T6, T7 et D2c
« résultat observé »). Sources : `app/lib/simulator/`, `app/lib/econ/simulate.js` (protégé,
`findThreshold` jamais appelé), `app/routes/app.simulator.jsx`, `decision_log` (I0-01), routes cron
existantes.

## 1. Ce qui existe

- S1 : 8 leviers, `runScenario` (avant / après / écart / fourchette / horizon), « Retenir ce
  scénario » → `decision_log` `simulated` avec `scenario` (`values`, `levers`, `overrides`,
  `assumptions`, `node`, `before`, `after`, `range`, `days`, `horizon`), `expected_impact_low/high`,
  `horizon_days` ; **`review_at`, `observed_impact`, `observed_at` restent vides**. Mémoire : les 5
  derniers scénarios avec « Rejouer » (URL).
- `findThreshold({ inputs, lever, node, target, lo, hi })` : bissection sur **un** levier du moteur,
  monotonie supposée ; renvoie `null` si la cible n'est pas encadrée. Les leviers d'écran
  « fulfilment » et « budget pub » ne sont pas des leviers du moteur mais des surcharges calculées
  après les leviers (`econOverrides`) : le mode objectif doit les traiter par une bissection propre
  sur `runScenario` (même principe), pas par `findThreshold` seul.
- Cron : 4 routes `api.cron.*` (Vercel Cron, `CRON_SECRET`, `maxDuration 300`) ; le nombre de crons
  autorisé dépend du plan Vercel (fait à vérifier avant d'en ajouter un).

## 2. Arbitrages

**W1 — Nœuds cibles du mode objectif.** (a) CM2 % seulement ; (b) CM2 %, CM2, résultat, BE-ROAS.
Recommandation : (b), même liste que le résultat du Simulateur.

**W2 — Leviers du mode objectif.** Un seul à la fois (T7). (a) Les 8 leviers ; (b) les 6 leviers
« facteur » (prix, panier, volume, retours, coût rendu, CAC), fulfilment et budget pub exclus tant
qu'ils sont des surcharges. Recommandation : **(a)** avec une bissection unique sur `runScenario`
dans un module pur `app/lib/simulator/objective.js` (bornes = bornes du levier, 40 itérations,
`null` si hors de portée) ; `findThreshold` du moteur reste intouché.

**W3 — Comparaison.** (a) 2 à 3 scénarios côte à côte : le scénario courant + des scénarios retenus
(URL `?compare=<id>,<id>`), table nœuds × scénarios avec écart et fourchette ; (b) uniquement des
scénarios retenus. Recommandation : (a). Les scénarios retenus se rejouent sur les feuilles du jour
(jamais les montants enregistrés) : le tableau dit « recalculé sur la période courante ».

**W4 — Quand calculer le résultat observé.** (a) À l'ouverture du Simulateur, pour les décisions de
la boutique dont `review_at ≤ maintenant` et `observed_at` vide (en arrière-plan, comme
`insight_log`) ; (b) cron quotidien pour toutes les boutiques ; (c) les deux. Recommandation : (a)
pour S2 (aucun cron nouveau, aucune question de plan Vercel), (b) plus tard avec les notifications.

**W5 — Définition de l'observé.** À J+30 : `observed_impact` = CM2 des 30 jours après la décision −
CM2 des 30 jours avant (mêmes fenêtres, feuilles réelles, `loadOverview` avec `now = decided_at +
30 j`, `days = 30` : courante = après, précédente = avant). Affiché « observé, toutes causes
confondues » à côté de l'attendu (fourchette) : jamais présenté comme l'effet du scénario. Si
l'historique ne couvre pas la fenêtre « avant » (boutique jeune), `observed_impact` reste vide avec
la raison.

**W6 — `review_at`.** Posé à la décision : `decided_at + horizon_days` (30 par mois glissant, sinon
la période). Modification I0-C côté action `keep` (aucune migration : la colonne existe).

**W7 — Offres.** T6 : aucune restriction en S2 tant que la tarification n'est pas décidée ; le code
ne lit le plan que par `plan.js`, facturation intouchée.
