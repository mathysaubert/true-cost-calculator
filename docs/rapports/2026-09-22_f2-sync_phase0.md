# F2 — Sync v2 (Shopify → base F1) : Phase 0

Date : 2026-09-22. Lecture seule : ce fichier est la seule écriture. Aucune ligne de code,
aucune migration, aucun réglage touché. Fait suite à `2026-09-22_refonte-phase0.md` (§4),
`2026-09-22_decisions.md` (décisions 6, 17, 19, 21 ; A2, A3, A9, A16, A17) et
`2026-09-22_f3-moteur_implementation.md` (feuilles attendues par le moteur).

## 0. Résumé exécutif

1. Aujourd'hui, la sync est un bulk de 30 jours (commandes + lignes), des remboursements
   paginés à part, un poll de 25 s et un upsert `order_margins` ; aucun webhook de commande,
   de remboursement, d'expédition ni de stock n'existe. F2 la remplace par trois flux :
   webhooks (temps réel), bulk (historique), réconciliation quotidienne (rattrapage).
2. **Sans `read_all_orders`, tout fonctionne sur les 60 derniers jours et s'accumule ensuite
   par webhooks** : CM1/CM2/CM3, seuils, retours, expédition, codes, nouveaux clients (l'index
   de commande vient de Shopify, pas de notre historique). Ce qui attend l'approbation :
   l'historique au-delà de 60 jours (cohortes, LTV, saisonnalité, comparaisons N-1, les
   seuils `minData` sur les nœuds lents). Détail en §3.
3. Deux prérequis qui ne dépendent pas du code : les nouveaux scopes (§6, décision 21) et
   l'accès aux **données clients protégées niveau 1** (sans lui, `customer.id` et le pays de
   livraison reviennent vides : cohortes et carte par pays absentes, le reste intact).
4. Contraintes vérifiées dans la documentation (§5) : 60 jours par défaut ; webhooks à
   acquitter en moins de 5 s, 8 nouvelles tentatives sur 4 h, dédoublonnage par
   `X-Shopify-Webhook-Id` ; en API 2025-10 une seule op bulk de requête à la fois, cinq en
   2026-01 ; résultats disponibles 7 jours ; `bulkOperations` remplace `currentBulkOperation`
   à partir de 2026-01 ; Vercel Hobby = cron une fois par jour (imprécision jusqu'à 59 min),
   fonctions 300 s.
5. Quatorze arbitrages en §7 (B1 à B14). Les bloquants : B1 (comportement avant
   `read_all_orders`), B2 (version d'API 2026-01), B5 (traitement des webhooks), B6 (plan
   Vercel et dispatcher), B7 (transition `order_margins`).

## 3. Ce qui est possible sans `read_all_orders`, ce qui l'attend

Fait vérifié : « Only the last 60 days' worth of orders from a store are accessible from the
Order object by default » (référence Order, 2025-10). La limite porte sur les **requêtes**
(`orders`, bulk compris). Les **webhooks** de commande exigent `read_orders` seulement : une
commande créée après l'installation arrive et reste dans notre base, sans limite de durée.
Conséquence : la profondeur d'historique d'une boutique = max(60 jours, temps depuis
l'installation de F2).

| Capacité | Sans `read_all_orders` (J0) | Ce que l'approbation ajoute |
|---|---|---|
| CA, CM1, CM2, CM3, résultat, seuils (BE-ROAS, BE-CAC, point mort), par jour / produit / canal / pays / code | Oui, sur 60 jours puis en continu | Recalcul sur 24 mois ; comparaisons N-1 |
| Nouveaux clients, BE-CAC, contribution par nouveau client | Oui : `customerJourneySummary.customerOrderIndex` donne le rang de la commande dans l'historique du client (test exclus), indépendamment de notre profondeur | Rien de plus pour le rang ; l'historique des clients existants pour la LTV |
| Cohortes, rachat, délai avant 2e achat, LTV/CAC | Partiel : cohortes à partir de l'installation seulement ; M+1 dès le 2e mois, M+3 au 4e | Douze cohortes M+12 complètes dès le backfill (décision 6) |
| Retours (motifs, taux, coût) | Oui pour les retours créés après l'installation (webhooks `returns/*`) ; la fenêtre de 30 j est respectée dès J+30 | Retours anciens : `Order.returns` est une connexion lisible dans le bulk 24 mois |
| Expédition (délai, OTD) | Oui pour les expéditions après l'installation ; historique 60 j via bulk (`fulfillments` sans événements) | Idem sur 24 mois ; les événements DELIVERED anciens dépendent de ce que le transporteur a écrit |
| Frais de paiement réels (Shopify Payments) | Oui : `balanceTransactions` n'est pas soumis aux 60 jours (à confirmer à l'implémentation, §5.6) | Rattachement aux commandes anciennes une fois celles-ci en base |
| Stock : couverture, point de commande | Oui, mais « 30 jours de ventes avant les jours de couverture » (Phase 0 refonte) : dès J+30 | Vitesse de vente moyenne sur 12 mois, saisonnalité |
| Seuils `minData` (A11) | Les nœuds à 200 sessions / 30 commandes attribuées / 20 premières commandes se débloquent au rythme réel de la boutique | Se débloquent immédiatement pour les boutiques actives |
| Saisonnalité, croissance glissante (A13) | Non (pas de N-1) | Oui |

Ce que F2 fait dès maintenant pour que l'approbation ne coûte rien plus tard : le backfill est
écrit par fenêtres mensuelles et borné par `shop_settings.history_months` (24) ; sans le scope,
la première fenêtre s'arrête à 60 jours (Shopify renvoie simplement moins de commandes, aucune
erreur documentée : à vérifier sur la boutique de dev) ; à l'approbation, un job
`orders_backfill` par mois manquant est créé et le reste suit (B1).

Coût de l'attente : chaque jour sans F2 installée est un jour d'historique perdu au-delà de la
fenêtre de 60 jours. Argument pour livrer F2 (webhooks + 60 j) avant l'approbation.

## 4. Architecture cible

### 4.1 Trois flux, un normaliseur

**Normaliseur unique** (pur, testé lot 25) : deux adaptateurs produisent la même forme interne
`OrderFacts` : `fromWebhookPayload` (JSON REST-like du webhook : `line_items[].tax_lines`,
`shipping_lines`, `discount_codes`, `source_name`, `test`, `taxes_included`,
`payment_gateway_names`, `customer.id`, `shipping_address.country_code`, `cancelled_at`,
`admin_graphql_api_id`) et `fromGraphqlNode` (nœud bulk ou requête : `lineItems.taxLines`,
`shippingLines`, `discountCodes`, `sourceName`, `test`, `taxesIncluded`,
`paymentGatewayNames`, `customer { id }`, `shippingAddress { countryCodeV2 }`,
`cancelledAt`, `purchasingEntity`, `customerJourneySummary`). Le lot 25 prouve l'égalité des
deux formes sur une même commande de fixture. Puis `computeLineEconomics` par ligne, exclusions
(§4.4), écriture `orders` + `order_margins`.

1. **Webhooks (temps réel)** : `orders/create`, `orders/updated`, `orders/cancelled`,
   `refunds/create`, `returns/request|approve|decline|close|cancel|reopen`,
   `fulfillments/create|update`, `fulfillment_events/create`, `inventory_levels/update`,
   `bulk_operations/finish`. Handler : `authenticate.webhook` (HMAC) → insertion
   `webhook_events` par `webhookId` (doublon = 200 immédiat) → traitement → statut
   `processed` ou `failed` → 200. Ce que le webhook ne porte pas (UTM, `customerOrderIndex`,
   frais) est marqué `attribution_ready=false` et rattrapé par le flux 3.
2. **Bulk (historique et rattrapage)** : une op par fenêtre mensuelle, pilotée par
   `sync_jobs` (`orders_backfill`, `window_start`, `window_end`, `bulk_operation_id`), fin
   d'op par `bulk_operations/finish` (charge utile en minuscules : `completed`, `failed`),
   téléchargement en flux, même normaliseur. Sous-ressources : voir B4.
3. **Réconciliation quotidienne** (cron existant 06:00) : bulk incrémental
   `updated_at:>=curseur` (commandes modifiées, remboursées, annulées ; rattrape les webhooks
   perdus), re-tirage des commandes `attribution_ready=false` de moins de 30 jours
   (`customerJourneySummary.ready`), frais Shopify Payments par `associatedOrder`, instantané
   quotidien du stock, rafraîchissement `customers_agg`.

### 4.2 Correspondance sources → tables F1

| Table | Source temps réel | Source historique / rattrapage | Champs sensibles |
|---|---|---|---|
| `orders` | `orders/create`, `orders/updated`, `orders/cancelled` | bulk `orders(query: created_at…)` ; réconciliation `updated_at` | `customer_id` (niveau 1), `country_code` (niveau 1) |
| `order_margins` (lignes) | mêmes webhooks | même bulk | aucun |
| `refunds` | `refunds/create` (`refund_line_items[].restock_type`, `transactions[].kind/status`, `refund_shipping_lines`) | requête paginée par fenêtre sur les commandes remboursées (chemin actuel) | aucun |
| `returns` | `returns/*` (scope `read_returns`) | connexion `Order.returns` dans le bulk (niveau 2 de profondeur, autorisé) | aucun |
| `fulfillments` | `fulfillments/create|update`, `fulfillment_events/create` (`status`, `happened_at`, `estimated_delivery_at`) | liste `Order.fulfillments` (scalaires) dans le bulk ; événements par requête paginée | aucun (pays de l'événement seul) |
| `order_fees` | aucun webhook | `shopifyPaymentsAccount.balanceTransactions` (`fee`, `net`, `associatedOrder`) ; règles manuelles sinon | aucun |
| `inventory_daily` | `inventory_levels/update` (`inventory_item_id`, `location_id`, `available`) | instantané quotidien `productVariants` (`inventoryQuantity`, `inventoryItem.tracked`, `unitCost`) | aucun |
| `customers_agg` | dérivée d'`orders` | recalcul quotidien | `customer_id` (niveau 1) |
| `shop_settings` | `shop { billingAddress { countryCodeV2 } ianaTimezone currencyCode taxesIncluded }` à la première sync | idem | aucun |
| `sync_jobs`, `webhook_events` | internes | internes | aucun |

### 4.3 Idempotence et immuabilité

- `orders` : upsert complet par `(shop_domain, order_id)` (le dernier webhook est la vérité :
  « treat the latest delivery as truth »).
- `order_margins` : `ignoreDuplicates` conservé sur les colonnes de snapshot ; les colonnes de
  faits mutables (`refunded_qty`, `restocked_qty`, `effective_qty`) sont mises à jour par
  `refunds/create` sans toucher au snapshot (contrat `ORDER_MARGINS_SNAPSHOT_COLUMNS`).
- `refunds`, `returns`, `fulfillments` : upsert par identifiant Shopify.
- `webhook_events` : clé `webhook_id` ; un même `X-Shopify-Event-Id` peut arriver sous deux
  `webhook_id` si deux abonnements existent pour un topic (un seul abonnement par topic chez
  nous).

### 4.4 Exclusions et données protégées

Exclusions (`ORDER_EXCLUSION_REASONS`) posées à l'ingestion : `test` (`Order.test`),
`cancelled` (`cancelledAt` non nul), `draft` (`sourceName = shopify_draft_order`),
`gift_card_only` (toutes les lignes `isGiftCard`), `b2b` (`purchasingEntity` de type Company
ou étiquette `shop_settings.b2b_tag`). Une commande exclue est conservée et comptée.

Données protégées : sans approbation niveau 1, « unapproved fields will be redacted » dans les
réponses API et les webhooks (doc « Work with protected customer data »). `customer.id` et
`shipping_address.country_code` reviennent vides ; l'ingestion ne doit jamais échouer sur un
champ vide, et l'écran dira « client non identifié » et « pays inconnu ». Rien de nominatif
n'est lu (décision c).

### 4.5 Dispatcher

Un job = une ligne `sync_jobs`. Le cron quotidien lit les jobs `pending` par boutique et les
exécute en séquence dans le budget de la fonction, puis se ré-invoque (fetch interne signé par
`CRON_SECRET`) tant qu'il reste des jobs et du temps. Concurrence : un job `running` par
boutique et par `kind` ; un job resté `running` plus de 30 min est repris. Format compatible
avec une file externe plus tard (décision 19).

## 5. Contraintes vérifiées dans la documentation (2026-09-22)

1. **60 jours** : référence `Order` 2025-10 (note en tête d'objet). Demande d'accès dans le
   Partner Dashboard ; exigence App Store 3.2.1 : ne demander `read_all_orders` que si
   nécessaire (texte de demande déjà rédigé dans `2026-09-22_decisions.md` §B).
2. **Données protégées** : niveau 1 = données client hors nom, adresse, téléphone, e-mail ;
   demande dans le Partner Dashboard ; champs non approuvés retournés vides ; les apps sur
   boutiques de développement n'ont pas besoin de la revue.
3. **Bulk** : en 2025-10, une seule op de requête à la fois par app et par boutique ; en
   2026-01 et plus, cinq simultanées ; jusqu'à cinq connexions, profondeur 2 ; résultats
   disponibles 7 jours ; op abandonnée après 10 jours ; `bulkOperations` et
   `bulkOperation(id:)` remplacent `currentBulkOperation` (déprécié) à partir de 2026-01 ;
   conseil doc : `sortKey` aligné sur le filtre (`created_at` + `CREATED_AT`) pour éviter les
   timeouts ; `bulk_operations/finish` livre `status` et `error_code` en minuscules.
4. **Webhooks** : délai de connexion 1 s, requête entière 5 s ; 8 nouvelles tentatives sur 4 h
   avec repli exponentiel ; dédoublonnage par `X-Shopify-Webhook-Id` (et `X-Shopify-Event-Id`
   pour corréler) ; « treat the latest delivery as truth » ; abonnements déclarés dans
   `shopify.app.toml` avec `topics`, `uri`, `include_fields` (réduit la charge utile), `filter`,
   `name` ; la version de sérialisation est `[webhooks].api_version` (2026-07 chez nous).
5. **Topics et scopes** : `orders/*` et `refunds/create` avec `read_orders` ; `returns/request`,
   `approve`, `decline`, `process`, `update` exigent `read_returns` (`cancel`, `close`,
   `reopen` acceptent `read_orders`) ; `fulfillment_events/create` avec `read_fulfillments` ;
   `inventory_levels/update` avec `read_inventory` (déjà accordé).
6. **Frais Shopify Payments** : `ShopifyPaymentsBalanceTransaction { fee, net, amount,
   associatedOrder { id }, sourceOrderTransactionId, type, test }` via
   `shopifyPaymentsAccount.balanceTransactions` ; scope `read_shopify_payments_payouts`. Le
   filtre par date de cette connexion n'a pas été vérifié : à confirmer avant d'écrire la
   pagination (risque : devoir lire tout l'historique de l'équilibre à chaque passage).
7. **Attribution** : `customerJourneySummary { ready, customerOrderIndex, daysToConversion,
   firstVisit, lastVisit { source, sourceType, utmParameters, landingPage } }` avec
   `read_orders` ; `ready=false` tant que les sessions attribuées ne sont pas créées ;
   fenêtre d'attribution 30 jours.
8. **Remboursements** : `refunds/create` porte `refund_line_items[].restock_type`
   (`no_restock`, `return`, `cancel`, `legacy_restock`), `subtotal`, `total_tax`,
   `transactions[].kind/status`, `refund_shipping_lines` : tout ce que A2 et la décision 1
   demandent, sans requête supplémentaire.
9. **Expédition** : `fulfillment_events/create` porte `status` (`delivered` en minuscules),
   `happened_at`, `estimated_delivery_at`, `country`, `order_id`, `fulfillment_id`.
10. **Stock** : `inventory_levels/update` porte `inventory_item_id`, `location_id`,
    `available`, `updated_at` ; la jointure article → variante passe par
    `InventoryItem.variant` (une requête ou le cache de l'instantané quotidien).
11. **Scopes ajoutés** : modification de `scopes` dans le TOML + `shopify app deploy` ; le
    marchand est invité à approuver à l'ouverture de l'app ; `app/scopes_update` se déclenche
    (handler existant). Les scopes optionnels existent (`optional_scopes`) pour ne demander
    `read_shopify_payments_payouts` ou `read_returns` qu'aux boutiques concernées (B13).
12. **Vercel** (docs du 2026-07 et 2026-08) : Hobby = 100 crons par projet, une exécution par
    jour maximum, déclenchement dans l'heure (jusqu'à 59 min de retard), fonctions 300 s par
    défaut et au maximum avec Fluid compute ; Pro = cron à la minute, 800 s. `waitUntil`
    (`@vercel/functions`, non installé) prolonge le traitement après la réponse, dans la même
    limite de durée que la fonction. Le commentaire « Hobby plafonne à 60 s » dans le code est
    périmé.
13. **Bibliothèques installées** : `@shopify/shopify-api` 13.0.0 expose `ApiVersion.January26`
    et `April26` ; `@shopify/shopify-app-react-router` 1.2.0 (`authenticate.webhook` renvoie
    `webhookId`, `apiVersion`, `subTopic`).

## 7. Arbitrages (options et implications)

**B1 (bloquant) — Comportement avant `read_all_orders`.**
(a) Livrer F2 avec backfill borné à 60 jours + webhooks ; à l'approbation, création automatique
des jobs mensuels manquants jusqu'à `history_months`. (b) Attendre l'approbation pour livrer
F2. (c) Comme (a) mais backfill manuel déclenché par un bouton Réglages après approbation.
Recommandation : (a). Chaque jour d'attente perd un jour d'historique ; la détection de
l'approbation se fait par `app/scopes_update` (scope présent dans `current`) ou par un test
quotidien de la profondeur retournée.

**B2 (bloquant) — Version d'API.** (a) Passer `apiVersion` à `2026-01` : `bulkOperations`,
`bulkOperation(id:)`, cinq ops simultanées (backfill parallèle), suppression de
`currentBulkOperation` déprécié ; à valider par le gate (les requêtes existantes, lot 22
marqueurs). (b) Rester en 2025-10 : une op à la fois, `currentBulkOperation` conservé.
Recommandation : (a) ; la version des webhooks est déjà 2026-07, l'écart entre les deux ne
pose pas de problème documenté mais deux versions cohabitent (à noter).

**B3 — Découpage du backfill.** (a) Fenêtres mensuelles séquentielles (24 ops au plus, une par
job). (b) Une op unique sur 24 mois (JSONL de plusieurs dizaines de Mo, un seul point
d'échec, URL 7 jours). (c) Fenêtres mensuelles avec jusqu'à 5 ops parallèles (2026-01).
Recommandation : (a) en V1, (c) si B2 = (a) et que la boutique de dev le prouve.

**B4 — Sous-ressources des commandes.** Contrainte : une connexion sous une liste est interdite
en bulk (`refunds` est une liste, `refundLineItems` une connexion). (a) Comme aujourd'hui :
remboursements par requête paginée sur les commandes `financial_status:refunded|partially_refunded`
de la fenêtre ; `returns` (connexion) et `fulfillments` (liste de scalaires) dans le bulk ;
événements d'expédition par requête paginée. (b) Tout par requêtes paginées, sans bulk pour les
sous-ressources. (c) Bulk séparé par ressource racine : il n'existe pas de requête racine
`refunds` ni `fulfillments`, donc (c) est impossible pour celles-ci.
Recommandation : (a).

**B5 (bloquant) — Traitement des webhooks.** (a) Traitement en ligne dans le handler (normaliser,
écrire `orders`, `order_margins`, `refunds`, `returns`, `fulfillments`), puis 200 ; la charge
utile suffit pour tout sauf l'attribution et les frais ; risque : dépasser 5 s si Supabase est
lent (chaque écriture est un aller-retour PostgREST ; viser 3 requêtes au plus). (b) Le handler
n'écrit que `webhook_events` avec la charge utile brute et répond ; un dispatcher traite ; sur
Hobby, la latence est de 24 h (cron quotidien), ce qui vide le « temps réel » de son sens. (c)
Comme (a) avec `waitUntil` pour les écritures secondaires (`customers_agg`) après le 200.
Recommandation : (a), avec (c) si `@vercel/functions` est ajouté (dépendance nouvelle, à
décider). `include_fields` réduit les charges utiles.

**B6 (bloquant) — Plan Vercel et dispatcher.** (a) Hobby : un cron quotidien (réconciliation +
dispatcher) ; backfill 24 mois par ré-invocations enchaînées dans la limite de 300 s par
invocation ; le premier backfill d'une boutique dure des heures de temps réel (une op bulk
par mois, chacune de quelques minutes côté Shopify) : acceptable si l'écran affiche
« historique en cours : 7 mois sur 24 ». (b) Pro : cron toutes les 5 minutes, 800 s, backfill
terminé dans l'heure ; coût mensuel. (c) File externe (Upstash QStash / Inngest) : un
fournisseur de plus. Recommandation : (a) si le plan reste Hobby, sans rien changer à
l'architecture pour (b). Je ne connais pas le plan actuel du projet : à confirmer.
